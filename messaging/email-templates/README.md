# Email templates for ItamarOS

These are **13 complete HTML templates** for hosted authentication and security notification flows. They use only the supported email template variables documented in https://supabase.com/docs/guides/auth/auth-email-templates.

## Installation

These HTML sources are **not yet applied** to the hosted project's mailer just because they are in GitHub.

1. Open **Authentication → Email Templates** for the ItamarOS account project (https://supabase.com/dashboard/project/slqjkysinhfkqjoigfuz/auth/templates).
2. For each supported message type, open the corresponding template and paste the full contents of its same-named `.html` file. Set its subject to the string in `subjects.json`; save.
3. Security notification types may need to be explicitly enabled separately in account authentication settings. An unenabled notification template will not cause an email to be sent.
4. Send a test invitation to an **email address you control**. Test Confirm sign up, Invite, Reset password, and Reauthentication separately, including real link behavior, spam placement, and display in Gmail mobile/desktop.
5. Do not expose SMTP credentials, API keys, recipient emails, tokens, or existing passwords in GitHub commits.

## Variables and security

- Use `{{ .ConfirmationURL }}` for signup confirmation, invitations, magic link, reset password and change email. This URL is generated by the authentication server. Never replace it with a static clickable destination.
- Use `{{ .Token }}` for reauthentication codes only. Never log these codes or send them to staff.
- Change email notification can use `{{ .OldEmail }}` and `{{ .Email }}`; phone changed uses `{{ .OldPhone }}` and `{{ .Phone }}`; identity notifications use `{{ .Provider }}`; MFA notifications use `{{ .FactorType }}`.
- Email links may expire or be consumed by overly aggressive antivirus scanners. If needed, configure a confirm-on-click landing page with an OTP flow separately and test it before replacing confirmation links.
- This package uses no remote images, email tracking pixels or click tracking. All buttons use HTTPS except the app-opening link shown only **after** identity verification on the website.
- For **manual invitations** created by the ItamarOS admin console: those are copied and sent manually, not sent automatically by the authentication server. Their text is generated in the console; do not assume the Invite template runs when using a generateLink-only flow.

## Troubleshooting failed delivery

The November 2 test invitation was accepted by the account API with **HTTP 200** around **12:31:42 UTC** and the logs showed an invitation event. An API success is **not a recipient delivery receipt**.
- Look at the sender Gmail account's **Sent** folder and the recipient account's Spam/All Mail/Promotions. Check for bounces or blocked recipients.
- Verify the SMTP server address, port, full username, app password, From address and that the Gmail account allows the configured sending method. Avoid pasting secret passwords into chat.
- A custom SMTP configuration can be saved but still fail later; test real inbox receipt and linked action.
- Check authentication logs and any sending provider events when they are available. If the email is not in Sent, investigate server/provider SMTP submission rather than assuming it was filtered.
- Check **Authentication → URL Configuration**. The project had a prior invitation using a localhost referer; configure `https://itamaros-web-emulator.onrender.com` as site origin and allowlist `/connect.html` and `/accept-invite.html` to avoid redirects to localhost.
- Google may apply per-account limits to SMTP, even if login works.
